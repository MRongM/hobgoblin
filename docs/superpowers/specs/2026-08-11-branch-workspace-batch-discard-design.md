# 子工作区批量丢弃改动设计

## 目标

在就绪子工作区的 More 菜单中增加“批量丢弃改动”。用户先在子工作区条目下方的内联面板检查各成员工作树的改动数量，再通过破坏性按钮一次确认；系统按仓库配置顺序丢弃所有有改动成员的全部未提交改动。

## 范围

- 菜单项只在子工作区完整就绪且没有其他批量 Git 动作执行时可用。
- 内联面板展示全部成员工作树、目标分支、改动数量和执行状态；干净成员明确显示为跳过。
- 不提供成员选择。执行范围固定为计划时所有有改动的成员工作树。
- 不新增右键菜单动作，不新增 HTTP 端点，不修改普通仓库“变更”页。
- 不使用 `git reset --hard`。

## 架构与数据流

沿用现有子工作区批量 Git 动作协议和 `/api/workspace/branch-workspaces/git-actions/*` 边界：

1. 渲染端从子工作区 More 菜单请求 `batch-discard` 计划。
2. 服务端按 manifest 顺序读取每个成员的工作树状态和完整补丁。
3. 每个计划成员记录精确变更路径、改动数量，以及由 HEAD、规范化状态和完整补丁共同生成的指纹。
4. 用户在内联面板确认后，仅提交计划 token；客户端不能改写路径范围。
5. 服务端重新验证未完成成员的指纹，再按顺序调用现有 `discardRepositoryChanges(repoId, worktreePath, paths)` 写路径。
6. 该写路径继续复用 `discardChangesForPaths`：对精确路径执行 tracked restore，并清理同一路径下的 untracked 文件和目录。
7. 每个成员独立记录成功或失败；失败不阻塞后续成员，已完成丢弃不回滚。批次结束后统一发布所有触达仓库的 snapshot invalidation。

## 安全与错误处理

- 计划 token 绑定完整内容，而不只绑定 Git 状态码，避免确认期间同状态文件的新编辑被静默丢弃。
- 路径来自服务端规范化的状态项，执行输入不接受客户端路径列表。
- 计划过期、成员漂移或内容变化时拒绝执行，并要求重新检查。
- 取消信号在成员边界生效；已完成成员保持完成。
- 单成员 restore 或 clean 失败时记录 `discard` 步骤、诊断和工作树路径，并继续后续成员。
- 即使 Git 在中途失败也会在批次结束后刷新触达仓库，因为 restore 可能已经产生部分写入。

## 界面与文案

- 菜单项和确认按钮保持同名：中文“批量丢弃改动”，英文“Batch discard changes”。
- 菜单项与按钮均使用破坏性视觉语义和 `RotateCcw` 图标。
- 描述明确覆盖已暂存、未暂存和未跟踪改动，并说明未跟踪内容无法从 Git 恢复。
- 复用现有批量动作内联面板、成员列表、阶段状态、失败汇总和 AI 错误交接，不引入新的视觉语言。
- 英文、简体中文、日文和韩文词典同步增加动作、描述、执行步骤与失败步骤文案。

## 测试

- 共享协议：接受 `batch-discard` 计划/执行输入，拒绝无 token 或额外路径形态。
- 计划层：精确收集路径和数量，完整补丁参与指纹，成员变化导致验证失败。
- 写层：只丢弃 dirty 成员；按 manifest 顺序执行；失败隔离；取消；延迟并集中 invalidation。
- 实时协议：允许 `batch-discard` 和 `discard` 活动状态。
- 渲染端：More 菜单动作、hook 执行输入、内联预览、无改动禁用、破坏性确认、失败重试。
- 词典：四种语言键完整且中文术语符合“子工作区/成员工作树”。

## 非目标

- 原子跨仓库回滚。
- 丢弃部分成员或部分文件。
- 自动执行、后台执行或跳过确认。
- 提供已丢弃内容的恢复机制。
- 修改子工作区生命周期删除/缩减语义。
