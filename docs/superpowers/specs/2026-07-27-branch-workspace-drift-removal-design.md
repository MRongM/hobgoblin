# 子工作区漂移成员移除与强删除设计

**日期**：2026-07-27  
**状态**：已实施；强制删除顺序按后续产品决策修订

## 背景

子工作区清单持久保存每个成员的目标分支与受管工作树路径。外部 Git 操作或未受保护的应用操作可能使受管路径改为检出其他分支，形成成员漂移。

当前读取逻辑会正确识别目标分支不再绑定受管路径，并将子工作区标记为“需要修复”。但成员减少和整个子工作区删除仍只通过清单目标分支查找工作树。当目标分支没有工作树、受管路径却由其他分支占用时，规划会返回“计划使用的目标路径已存在”，导致异常成员无法移除，整个子工作区也无法删除。

## 目标

1. 在异常成员行的菜单中提供“移除成员工作树”。
2. 允许从子工作区移除一个发生漂移的成员工作树。
3. 允许在漂移状态下强删除整个子工作区。
4. 删除受管路径当前实际绑定的工作树，而不是假设它仍绑定清单目标分支。
5. 保留清单目标分支、实际检出分支和远程分支，除非用户在整个子工作区删除流程中明确选择现有的目标分支清理选项。
6. 复用现有计划、审批、执行前重建校验、进度持久化、取消和恢复机制。

## 非目标

- 不自动修复或切换漂移成员的分支。
- 不自动认领位于其他路径的目标分支工作树。
- 不允许单成员移除删除最后一个成员；最后一个成员仍需通过整个子工作区删除处理。
- 不绕过主工作树或锁定工作树保护。
- 不新增绕过计划、审批、精确路径、主工作树或锁定工作树边界的递归删除入口。
- 不更改正常成员的菜单或普通仓库工作树生命周期。

## 术语与身份

本设计沿用 `CONTEXT.md` 中的现有术语，不新增领域概念。

- **清单目标分支**：成员清单中的 `targetBranch`，表示子工作区预期使用的分支。
- **受管工作树路径**：成员清单中的 `worktreePath`，是成员生命周期操作拥有的精确路径。
- **实际检出分支**：仓库权威快照中当前绑定受管工作树路径的分支。它可能与清单目标分支不同。

工作树身份以“仓库边界 + 精确路径”为准。分支名不是删除目标的唯一身份。

## 交互设计

### 异常成员菜单

当成员不可用且子工作区没有正在运行的操作时，成员行菜单显示“移除成员工作树”。该动作打开现有“移除成员工作树”对话框，并预选、锁定当前成员。

如果成员路径仍绑定该仓库的有效工作树、只是实际签出分支与清单目标分支不一致，成员行不再整体禁用。Renderer 按实际分支提供导航、编辑器、终端和既有成员分支动作，并显示低强调的“需要修复”提示。无法在成员路径解析到注册工作树的异常成员仍保持不可导航。

正常成员继续通过子工作区项目菜单中的既有“移除成员”入口批量选择，不在本次改动中增加重复入口。

以下情况不显示或禁用异常成员删除：

- 子工作区只剩一个成员；
- 删除或减少成员操作正在继续；
- 子工作区存在活动操作；
- 成员已处于 `removed` 进度。

### 强删除整个子工作区

“需要修复”状态下保留现有“删除子工作区”入口和确认对话框。删除规划改为支持路径与目标分支不一致的成员，不再因受管路径存在而直接返回 `target-exists`。

对话框继续展示精确计划步骤和既有审批项，并在检查界面提供独立的“强制删除”按钮。强删除不是无确认的文件系统删除。

独立强制删除沿用同一计划令牌和审批，但采用异常清理顺序：先关闭已批准的内部终端，再递归删除计划绑定的精确子工作区根目录、清理应用清单，最后尽力清理各成员工作树登记。成员登记清理失败只产生警告，不恢复已经删除的目录或配置；该路径不执行本地分支或上游分支删除。

## 服务端规划

### 路径绑定解析

为成员减少和整个子工作区删除复用一个路径绑定解析规则：

1. 读取成员仓库的权威快照，并包含工作树状态。
2. 在所有分支工作树中按规范化后的精确 `member.worktreePath` 反向查找实际工作树。
3. 独立读取清单目标分支，用于可选的目标分支清理和远端信息。
4. 不再以“目标分支是否拥有工作树”决定受管路径是否可移除。

规划结果明确区分：

- `targetBranch`：清单目标分支；
- `checkedOutBranch`：受管路径实际检出的分支；仅在实际工作树存在时提供；
- `worktreePresent`：受管路径是否为该成员仓库注册的工作树。

### 异常成员减少

对显式选中的异常成员：

- 受管路径绑定该仓库任意非主、未锁定工作树：计划按实际分支与精确路径移除工作树。
- 受管路径不存在：工作树步骤视为已满足，仅移除成员记录。
- 清单目标分支工作树位于其他路径：保留该工作树，不移动、不删除；仍可移除当前成员记录。
- 受管路径存在但不是该仓库注册的工作树：拒绝单成员删除，避免把普通内容或其他仓库内容误当作成员工作树。
- 实际工作树脏：要求 `discard-member-changes` 审批。
- 受管路径下有内部终端：要求 `close-terminals` 审批。

未选中的成员必须保持可用；减少操作不得借清理一个异常成员之机忽略其他成员漂移。

### 强删除整个子工作区

对清单中的每个成员路径：

- 路径绑定该成员仓库的实际工作树：按实际分支与精确路径强制移除工作树。
- 路径不存在：视为已移除。
- 路径存在但不是该成员仓库注册的工作树：将其视为未纳管内容，要求 `unmanaged-content` 审批，并在工作树步骤之后按精确路径删除。
- 路径绑定主工作树或锁定工作树：拒绝计划，保持不可绕过的安全边界。

目标分支位于其他路径不再阻断整个子工作区删除，也不会被移动或作为受管工作树删除。

整个子工作区删除继续沿用：

- 修改过的复制内容审批；
- 未纳管内容审批；
- 内部终端关闭审批；
- 可选的清单目标本地分支及上游分支清理；
- 分步进度持久化、取消和失败后继续；
- 计划令牌与执行前权威重建校验。

## 执行语义

工作树移除调用使用 `checkedOutBranch` 和 `worktreePath`。`targetBranch` 只用于现有的可选分支清理逻辑，避免把实际占用分支误删。规划为已满足的缺失成员不再调用 Git 删除，只更新清单进度。

执行顺序保持：

1. 关闭已批准的内部终端；
2. 持久化操作中间态；
3. 逐个移除计划中的实际工作树并持久化成员进度；
4. 处理可选目标分支和上游清理；
5. 删除附加项及已批准的未纳管内容；
6. 删除子工作区根目录；
7. 删除或更新清单记录并发布失效通知。

执行前重新构建计划并比较令牌。如果实际分支、路径绑定、脏状态、锁定状态、终端或目录内容发生变化，旧计划不得执行。

## 错误处理与安全

- 单成员删除遇到非工作树路径占用时返回明确的“成员路径不是受管工作树”错误，不使用通用 `target-exists`。
- 主工作树和锁定工作树继续返回现有专用错误。
- 无法确定工作树脏状态时拒绝单成员删除。
- 无法读取仓库、目录、终端或指纹时关闭失败，不生成不完整计划。
- 删除符号链接时只删除链接，不跟随其目标。
- 未批准的脏改动、内部终端或未纳管内容不得删除。
- 整个子工作区删除可以丢弃受管工作树未提交改动，延续现有删除语义和警告。

## 分层与状态同步

- 共享契约继续由 `src/shared/branch-workspaces.ts` 拥有，仅增加计划所需的实际分支字段。
- 规划规则留在 `src/server/modules/branch-workspace-plan.ts`。
- 顺序执行和进度持久化留在 `src/server/modules/branch-workspace-write-paths.ts`。
- 路由和客户端协议保持薄层；同一执行接口用显式强制标志区分检查界面的独立动作，不新增平行删除接口。
- Renderer 只负责打开现有对话框并投影异常成员菜单；权威判断全部在服务端重新完成。
- 成功、失败和取消继续通过既有 invalidation/refetch 路径收敛到各窗口。

## 测试策略

### 规划测试

- 异常成员的实际分支与目标分支不同时，减少计划使用实际分支移除工作树并保留目标分支。
- 整区删除在相同漂移下生成工作树移除步骤，不返回 `target-exists`。
- 目标分支工作树位于其他路径时保留该工作树。
- 受管路径缺失时计划视为已满足。
- 单成员路径被普通内容占用时拒绝。
- 整区删除遇到普通内容占用时要求 `unmanaged-content` 审批。
- 主工作树和锁定工作树仍拒绝。
- 脏实际工作树与内部终端生成对应审批。

### 执行测试

- 移除工作树时传递 `checkedOutBranch`，分支删除仍只针对 `targetBranch`。
- 单成员删除后只移除所选清单成员。
- 整区强删除按步骤删除实际工作树、批准内容、根目录和清单。
- 执行前路径绑定变化导致计划令牌失效。
- 中途失败保留可继续的操作进度。

### UI 测试

- 异常成员菜单显示“移除成员工作树”。
- 正常成员不增加重复的单成员删除入口。
- 最后一个成员不提供单成员删除。
- 点击异常成员删除会打开减少成员对话框并固定预选该成员。
- 分支漂移但路径有效的成员显示弱“需要修复”提示，并按实际分支保持大部分功能可用。
- “需要修复”状态下的整个子工作区删除可以展示强删除计划及审批。

## 设计取舍

选择扩展现有 `reduce` 和 `remove` 生命周期，并用同一执行接口的显式标志承载独立强制删除动作，而不是新增 `force-remove` 状态机操作：

- 复用已经验证的审批、计划令牌、进度恢复和失效通知；
- 避免两套删除语义漂移；
- 将变化限制在工作树目标解析，不扩大持久状态机；
- 保持 KISS、DRY 和 YAGNI。

不创建 ADR：该决策局限于现有子工作区删除策略，复用既有架构，且可通过局部实现调整。
