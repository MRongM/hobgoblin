# 子工作区批量合并冲突 AI 接管设计

**日期**：2026-07-30  
**状态**：已实施并验证

## 背景

子工作区的批量合入与批量合出已经按清单顺序逐成员执行、遇首个失败停止，并在前台弹窗中保留失败成员、步骤和 Git 错误。普通工作树的合并冲突已经支持 AI 接管：选择可用的 Codex 或 Claude，打开冲突工作树的内部终端，填入可审阅命令但不自动执行。

子工作区需要同等的恢复入口，但终端目标不同：接管必须进入子工作区根目录终端，使 AI 从整个子工作区上下文定位失败成员。批量合出还可能在应用临时工作树中执行；该现场会在失败后清理，因此不能仅凭 `reason: 'merge-conflict'` 展示接管。

## 目标

1. 批量合入或批量合出在 Git 确认发生合并冲突且冲突工作树仍被保留时，展示 Codex / Claude AI 接管入口。
2. 接管选择或创建子工作区根目录的 Native 内部终端，而不是失败成员终端或合出目标终端。
3. 填入的命令明确指出失败仓库与实际冲突工作树，使根目录中的 AI 能定位现场。
4. 命令只进入可编辑输入框，不附加回车，不自动执行，也不自动运行 `git add`、`git commit` 或 `git merge --continue`。
5. 保持普通工作树 AI 接管、批次停止/重试、临时工作树清理和多窗口终端语义不变。

## 非目标

- 不为拉取、推送、计划过期、网络错误、取消或普通 Git 失败提供 AI 接管。
- 不保留、暴露或重新创建已经清理的应用临时工作树。
- 不在失败成员工作树终端内接管。
- 不自动解决、暂存、提交或继续合并。
- 不增加 AI 提供商、全局设置、后台任务、持久接管状态或新依赖。

## 已确认决策

- 接管终端是子工作区根目录终端。
- 只处理服务端确认的合并冲突。
- 只有明确返回保留冲突现场时才展示接管；临时工作树冲突不展示。
- 成功填入命令后关闭批量合并弹窗并显示根目录终端；填入失败时保留弹窗和原错误。
- 复用普通工作树的提供商探测、按钮状态、打开终端选择规则和“只填入不执行”安全边界。
- 实施采用当前会话 inline 执行，不启用子代理，不创建 Git 提交。

## 方案比较

### 方案 A：Renderer 从计划和失败原因推断现场

Renderer 可用失败成员、所选目标和计划中的 `worktreePath` 推断接管位置。改动较少，但计划描述的是执行前事实；更重要的是临时工作树冲突在清理后仍可能携带 `merge-conflict`，容易展示一个无法处理的入口。

### 方案 B：服务端显式返回保留冲突现场（采用）

失败成员结果增加可选 `conflictWorktree: { branch, path }`。服务端只有在合并步骤返回 `merge-conflict` 且该路径未被清理时才附加它。Renderer 不猜测 Git 或清理状态，只在字段存在时展示接管。

该方案与普通工作树合出结果的 `conflictWorktree` 语义一致，保持服务端拥有 Git 事实，且无需新增读取或状态同步路径。

### 方案 C：服务端直接启动 AI 或保留临时冲突现场

这会跨越现有终端输入安全边界，或改变临时工作树生命周期和清理保证，代价与风险均明显超出本需求，不采用。

## 协议与领域模型

共享 Git 类型提供通用冲突工作树：

```ts
interface GitConflictWorktree {
  branch: string
  path: string
}
```

`BranchWorkspaceGitActionMemberResult` 增加：

```ts
conflictWorktree?: GitConflictWorktree
```

字段约束：

- 仅失败成员可携带。
- 仅 `step === 'merge'`、`reason === 'merge-conflict'` 且现场保留时可携带。
- 批量合入现场是成员目标分支与成员工作树。
- 批量合出复用现有目标工作树时，现场是所选目标分支与该工作树。
- 批量合出使用应用临时工作树时，清理后不得携带该字段。
- 清理本身失败时返回清理失败，不提供冲突接管。

仓库级合出结果继续保留现有导出名称，并可将其冲突类型别名到通用 `GitConflictWorktree`，避免重复结构。

## 终端接管边界

现有 `ai-terminal-handoff` 的会话选择与写入流程抽成面向 `TerminalSessionBase` 的窄核心：

1. 确认终端命令桥可用。
2. 激活目标展示上下文。
3. 读取该目录的终端快照。
4. 优先复用已选中的 `open` 会话，否则复用第一个 `open` 会话。
5. 没有可用会话时，以完整 `TerminalSessionBase` 创建 Native 终端。
6. 等待外部输入可写后填入命令，不发送回车。

普通工作树适配器继续使用 `{ repoRoot, branch, worktreePath }`。子工作区适配器使用：

```ts
{
  repoRoot: workspaceRootId,
  branch: branchWorkspace.branch,
  worktreePath: branchWorkspace.path,
  targetKind: 'branch-workspace',
  branchWorkspaceId: branchWorkspace.id,
}
```

激活回调清除成员选择并选择子工作区根上下文；紧凑布局同时切换到 detail 表面。终端会话仍由现有 server-backed registry 管理，不增加 Renderer 持久状态。

## AI 命令

提供商命令继续通过共享 `buildAiHandoffCommand()` 构造并使用 JSON 字符串编码提示词。子工作区提示词包含：

- 失败仓库名；
- 权威冲突工作树路径；
- 当前终端位于子工作区根目录；
- 只检查冲突文件并做最小修改；
- 禁止自动执行 `git add`、`git commit` 和 `git merge --continue`。

路径和仓库名只作为已编码的提示词内容进入终端，不参与 shell 拼接。命令末尾不含换行。

## UI 与交互

普通工作树与子工作区共享一个合并冲突 AI 操作块：

- 标题沿用 `AI handoff / AI 接管`；
- 只显示探测为可用的 Codex / Claude；
- 任一接管进行中时禁用全部提供商按钮；
- 失败时在操作块内显示错误；
- 成功时调用调用方的完成回调。

子工作区批量合入、批量合出弹窗在原错误之后、Footer 之前渲染该操作块。展示条件是当前结果中恰有失败成员携带 `conflictWorktree`；普通错误、只有 `reason` 而无现场、非合并批次均不显示。

用户选择提供商后：

1. 选择子工作区根上下文；
2. 打开或复用根目录终端；
3. 填入上下文化命令；
4. 成功后关闭批量弹窗，使终端可直接操作；
5. 失败时保持弹窗、Git 错误和重试状态不变。

## 状态与分层

- Git 冲突原因、现场保留与临时清理事实：服务端写路径拥有，随执行结果返回。
- 提供商可用性：沿用现有查询，不新增持久状态。
- 按钮 pending/error：合并冲突操作组件本地状态。
- 批量计划、结果和重试身份：继续由现有 hook 与服务端活动状态拥有。
- 子工作区选择：复用 `activateBranchWorkspace()`，不创建新的导航 store。
- 终端会话：继续使用运行时一致的终端 registry 和命令桥。

不增加新 route、source 层、runtime facade、realtime 事件或 Electron 专用分支。

## 错误处理与边界场景

- 提供商探测失败：不显示按钮，不遮蔽原合并错误。
- 终端桥不可用、终端创建失败或输入未就绪：接管返回失败，弹窗保持打开并显示错误。
- 已选终端不是 `open`：不复用；优先其他 `open` 会话，否则创建新会话。
- 批量合入冲突：始终可指向成员工作树。
- 批量合出到现有工作树的冲突：指向该目标工作树，即使路径位于子工作区根目录之外。
- 批量合出到临时工作树的冲突：现场清理后不显示接管。
- 只有 `reason: 'merge-conflict'` 但缺少 `conflictWorktree`：按不可接管处理。
- 接管成功后不把批次标记为成功；用户解决或中止冲突后重新打开操作获取新计划。

## 测试策略

### 服务端写路径

- 批量合入冲突返回失败成员的目标分支和成员工作树。
- 批量合出到现有工作树的冲突返回目标分支和目标路径。
- 批量合出临时工作树冲突完成清理且不返回现场。
- 普通 merge 失败、pull/push/cleanup 失败不返回现场。

### 终端接管

- 通用目标接管保留完整 `TerminalSessionBase`，包括 `targetKind` 与 `branchWorkspaceId`。
- 激活目标后复用已选 `open` 根终端；没有时创建 Native 根终端。
- 等待输入就绪并只填入命令，不附加换行。
- 子工作区命令包含失败仓库和冲突路径，特殊字符经编码后不形成额外 shell 语句。

### Renderer

- 合入和合出弹窗只在失败成员携带保留现场时显示操作块。
- 普通错误和已清理临时冲突不显示。
- 点击提供商传递失败仓库与现场；成功关闭弹窗，失败保留弹窗并显示接管错误。
- `WorkspaceRepositoryRail` 激活子工作区根上下文并构造带 `targetKind: 'branch-workspace'` 的终端目标。
- 普通工作树的现有 AI 接管组件测试继续通过。

### 全量验证

```text
bun run typecheck
bun run test
bun run check:architecture
git diff --check
```

## 架构压力检查结论

- **事实所有权**：是否存在可处理现场由服务端明确给出，Renderer 不从错误字符串或旧计划推断。
- **临时路径安全**：接管不会阻止、绕过或逆转应用临时工作树清理。
- **终端身份**：根终端携带子工作区目标身份，复用现有目录级终端键和会话生命周期。
- **DRY**：提供商探测、按钮状态和终端选择/填入流程与普通工作树共享；只有目标适配和提示词上下文不同。
- **KISS/YAGNI**：只增加一个可选结果字段和一个 Renderer 接管适配，不增加持久状态、后台流程或自动执行。
- **故障可解释**：原 Git 错误始终保留；接管失败有独立错误；无法保留的现场不提供误导入口。

不创建 ADR：该设计沿用现有 AI 接管和批量合并边界，是可逆的功能扩展，没有形成新的跨系统、难以逆转的平台决策。

## 实施与验证结果

- 服务端只为保留的合并冲突现场返回 `conflictWorktree`；应用临时工作树完成清理后不返回该字段。
- 普通工作树与子工作区复用同一 AI 操作块和目录级终端填入核心；子工作区接管始终激活根目录终端。
- 已按 TDD 完成服务端、终端、共享 hook、弹窗和 Rail 集成回归。
- `bun run test`：380 个测试文件、3587 个测试通过。
- `bun run typecheck`：main、web、test 三套 TypeScript 工程通过。
- `bun run check:architecture`、变更文件 Prettier 检查和 `git diff --check` 通过。
