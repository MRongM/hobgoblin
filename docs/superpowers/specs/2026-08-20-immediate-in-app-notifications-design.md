# 应用内通知即时显示设计

## 目标

应用内通知由当前渲染器的共享通知面即时显示，不再依赖产生事件的仓库 `RepoView` 是否已挂载。用户在子工作区根上下文发起成员工作树操作时，可以停留在子工作区查看结果；切换到其他项目、子工作区或工作树后，尚未完成的操作也在完成时立即通知。

## 现状与问题

应用级 `Toaster` 已常驻在主窗口覆盖层中，但仓库事件的消费器 `useRepoToasts(repoId)` 挂载在当前 `RepoView`。子工作区由父工作区的 `RepoView` 承载，成员仓库事件不会被消费；事件留在成员仓库队列中，直到用户切换到该仓库工作树并挂载对应 `RepoView` 后才弹出。

这种行为把应用内通知错误地绑定到了导航生命周期，也与 `CONTEXT.md` 中“当前渲染器共享通知面”的定义不一致。

## 方案选择

采用应用壳层统一消费仓库事件：在共享 `Toaster` 同级挂载一个常驻仓库通知监听器，监听当前渲染器内所有已打开仓库的事件队列。

未采用的方案：

- 只在当前子工作区监听成员仓库。离开子工作区后监听器会卸载，异步完成通知仍可能延迟。
- 给所有仓库事件新增子工作区来源标识。现有需求只要求即时交付，不要求按来源重新路由；扩展所有写路径和事件类型没有当前收益。

## 行为约束

- 任一已打开仓库产生应用内通知事件后，当前渲染器立即显示，不受当前项目、子工作区、成员工作树或普通工作树选择影响。
- 子工作区批量操作已经产生的逐成员通知保持逐成员显示；不新增批量汇总通知。
- 保留现有成功、错误、信息和警告级别、文案、描述、通知 ID 与显示时长。
- 每个事件只显示一次；显示后按仓库和事件 ID 精确清除。
- 清除时不得删除同一仓库在本轮渲染后追加的新事件。
- 应用内通知继续仅属于当前渲染器，不持久化，也不跨窗口同步。

## 组件与数据流

`App` 的主窗口覆盖层负责同时挂载共享 `Toaster` 和常驻仓库通知监听器。监听器从 `useReposStore.repos` 读取所有仓库的本地事件队列，复用现有通知格式化逻辑逐条调用 `sonner`，再调用 `clearEvents(repoId, consumedEventIds)` 精确确认已显示事件。

`RepoView` 不再挂载仓库通知消费器。仓库页面继续只负责仓库内容与交互，通知交付归还给应用级覆盖层，避免同一事件存在两个消费者。

本次不修改服务端、实时协议、仓库写路径或批量 Git 协议。现有生产者仍把结果写入相同的渲染器本地仓库事件队列。

## 异常与并发

- 仓库事件为空时监听器不产生通知或状态写入。
- 多个仓库同时产生事件时，各事件沿用自己的稳定通知 ID，不互相覆盖。
- 消费期间追加的新事件拥有不同事件 ID；精确清除已消费 ID 后，新事件保留并在下一轮显示。
- 仓库关闭会移除其渲染器本地状态；本次不新增关闭后通知恢复或持久化语义。

## 测试

- 回归测试：仅挂载应用级监听器、当前活动仓库为子工作区父级时，成员仓库已有结果事件也立即显示并被清除。
- 多仓库测试：不同仓库的事件分别使用仓库作用域 ID 显示，各自只消费一次。
- 兼容测试：工作树 bootstrap 的多行成功描述继续使用现有格式。
- 完成前运行 `bun run test`、`bun run typecheck` 和 `bun run check:architecture`。

## 工程原则

- **KISS / YAGNI**：移动消费边界并复用现有格式化逻辑，不扩展服务端协议或新增通知来源模型。
- **DRY**：应用中只保留一个仓库事件通知消费入口。
- **SOLID**：`RepoView` 负责仓库视图，应用级监听器负责当前渲染器的通知交付。
