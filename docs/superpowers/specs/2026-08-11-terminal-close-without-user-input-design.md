# Terminal Close Without User Input Design

## Goal

Close an internal terminal immediately when no user input has been accepted by that terminal. Preserve the existing confirmation for terminals that have received user input or whose input history is unknown.

This applies to single-session close actions:

- the close button on a regular terminal tab;
- the close button in the compact terminal switcher;
- the terminal tab context-menu action to close the current session.

Closing other terminals or all terminals remains a bulk destructive action and continues to require confirmation.

## Input Semantics

“User input” means non-empty user-intent data accepted while the renderer controls the terminal. It includes keyboard input, paste, drop, toolbar/command input, and extra-key input.

The following do not count:

- terminal-emulator protocol replies generated by xterm;
- input attempted while the renderer is only a viewer and cannot write;
- empty input;
- resize, scroll, paging, takeover, output, or title events.

The state is monotonic for a server terminal session: it begins as `false` and becomes `true` on the first accepted user-intent write. Restarting the PTY within the same server session does not clear it. Closing the session removes the state with the session.

## Considered Approaches

1. **Renderer-local input timestamp.** Reuse `lastTerminalInputAt`. This is small, but a second renderer or a reattached renderer cannot distinguish an untouched terminal from lost input history.
2. **Infer input from terminal output or process state.** This cannot reliably distinguish a shell prompt, program output, and the echo of a command.
3. **Server-owned input state with a renderer projection — selected.** The terminal session manager owns the runtime-coherent fact, while the controlling renderer updates its projection immediately and the server broadcasts one catalog invalidation on the first user input.

The selected approach follows the existing server-first terminal model and keeps cross-window behavior convergent without broadcasting every keystroke.

## Protocol and Server State

Add an optional `userIntent` boolean to `TerminalWriteInput`.

- Omitted means user intent, preserving existing callers.
- `false` identifies a batch containing terminal-emulator protocol data only.
- A mixed batch is user input and omits the field.

`ManagedTerminalSession` tracks whether its pending write batch contains any user-intent data. Its existing input callback fires only for accepted, non-empty user input.

`TerminalSessionManager` stores `hasUserInput` on each session. On the first accepted user-intent write it:

1. changes the state to `true`;
2. queues the PTY write as usual;
3. emits a one-time session-input event.

The terminal server turns that event into the existing `sessions-changed` invalidation. Renderers refetch the terminal catalog through the current query path. No new realtime message type or continuous stream is introduced.

The server terminal summary exposes optional `hasUserInput` for wire compatibility. New servers always emit a boolean. Missing data is treated as unknown, never as evidence that no input occurred.

## Renderer Projection

`TerminalSessionRegistry` keeps the latest input-state projection per terminal key.

- A server `true` value and a locally observed user input are monotonic for the same session ID.
- A new server session ID replaces the old projection with the new server value.
- A missing server value projects conservatively as `true`, so the UI still confirms.
- Local user input changes the projection to `true` immediately, before the server refetch completes.
- Terminal-emulator replies continue to be written but do not change the projection or the echo-suppression timestamp.

The web `TerminalSessionSummary` exposes the projected state. `false` is the only value that permits confirmation-free close; `true` and an omitted value require confirmation.

## Close Interaction

Centralize single-terminal close execution so confirmed and immediate paths preserve the same behavior:

- compute and restore focus to the adjacent tab when the active tab closes;
- preserve the existing asynchronous tmux error handling;
- reset dialog-local state after a successful close.

When a single close is requested:

1. find the target summary;
2. if `hasUserInput === false`, execute the ordinary close immediately;
3. otherwise open the existing confirmation dialog.

An untouched tmux-backed terminal also closes immediately using the ordinary close behavior. It detaches/closes Hobgoblin's terminal session without opting into the dialog-only “close exact tmux session” action.

Bulk close behavior is unchanged, even when every target is untouched.

## Testing

Use test-first changes to cover:

- protocol normalization accepts boolean `userIntent` and rejects invalid values;
- the manager starts at `hasUserInput: false`, ignores protocol-only writes, flips once on user input, and emits one input-state event;
- `ManagedTerminalSession` attributes user, emulator-only, and mixed batches correctly;
- the registry projects server state, updates immediately after local input, treats missing state conservatively, and resets for a replacement session ID;
- single close buttons and “close current” bypass confirmation only for explicit `false`;
- input-bearing and unknown terminals still require confirmation;
- bulk close still requires confirmation;
- immediate close preserves adjacent-tab focus and ordinary tmux close semantics.

Run focused tests first, then:

- `bun run typecheck`
- `bun run test`
- `bun run check:architecture`

## Non-Goals

- Do not persist input history across server restarts.
- Do not infer input from output or shell state.
- Do not remove confirmation from bulk close actions.
- Do not redesign the terminal close dialog or add settings/copy.
- Do not automatically kill an underlying tmux session when skipping the dialog.

## Design Principles

- KISS: add one monotonic session fact and reuse the existing catalog invalidation path.
- DRY: use one close executor for immediate and confirmed single-session closes.
- YAGNI: add no persistence, new realtime transport, setting, or UI copy.
- SOLID: the server owns runtime truth, the registry owns projection, and the tab component owns interaction state.
