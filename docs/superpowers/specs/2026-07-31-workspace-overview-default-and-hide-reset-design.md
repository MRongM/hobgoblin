# 工作区概览默认激活与隐藏联动设计

**日期**：2026-07-31  
**状态**：已确认，授权内联自主实施

## 问题

多仓库工作区的“隐藏工作区仓库”动作目前只改变仓库列表可见性。若用户正在查看一个成员仓库，仓库的工作树导航和文件区仍然保留，导致隐藏动作只移除了上方列表，没有退出仓库上下文。

顶层工作区激活目前会恢复 `workspaceActiveContextByRoot` 记录的上次仓库或子工作区上下文。用户希望工作区主目录成为统一默认入口，而不是在首次打开、切换回来或会话恢复时自动进入某个 Git 仓库或子工作区。

## 目标

- 隐藏工作区仓库列表时，同时退出成员仓库或子工作区上下文并激活工作区概览。
- 激活工作区概览后，不再展示成员仓库的工作树区域。
- 隐藏工作区仓库列表时显式收起桌面文件区；重新显示列表时不自动展开文件区。
- 首次打开、项目切换、项目循环切换、关闭项目后的回退及会话恢复，统一默认激活工作区概览。
- 独立 Git 仓库和普通目录项目的激活、恢复行为保持不变。

## 方案比较

### 采用：由动作发起处组合明确意图

`WorkspaceRepositoryRail` 在列表由显示切换为隐藏时，组合三个已有边界清晰的意图：收起文件区、激活工作区概览、隐藏仓库列表。文件区仍由 `RepoView` 或 `BranchWorkspacePane` 的局部 React 状态拥有，Rail 只接收一个明确的 `onCollapseFileArea` 回调。

顶层项目选择入口统一把多仓库工作区解析到根目录及 `{ kind: 'overview' }`，不再使用已保存的成员上下文作为默认激活目标。

该方案没有派生 effect，没有跨层读取局部展示状态，用户动作与状态转换一一对应。

### 不采用：监听仓库列表可见性的 React effect

effect 会把用户动作变成隐式副作用，并在会话恢复、响应式切换或外部状态写入时重复触发，容易产生中间帧和难以追踪的导航变化。

### 不采用：把文件区折叠状态移入 Zustand

文件区可见性是当前 renderer 的短期展示状态。将其持久化或放入全局 Store 会违反 `docs/state-sync.md` 的 Local state 规则，也会扩大跨窗口和恢复语义。

## 交互设计

### 隐藏工作区仓库

当仓库列表当前可见时点击隐藏按钮：

1. 将当前 renderer 的文件区设为收起；已经收起时保持收起。
2. 激活工作区概览，将 `activeId` 设为工作区根目录，并把活动上下文设为 `{ kind: 'overview' }`。
3. 将该工作区的仓库列表可见性设为隐藏。

切回工作区概览后，成员仓库的 `RepoExplorerPane` 被根目录的 `PlainWorkspacePane` 替代，因此“工作树”区域随仓库上下文一起消失。子工作区成员上下文也会退出，子工作区列表本身仍按既有隐藏态布局显示。

当仓库列表当前隐藏时点击显示按钮，只恢复仓库列表，不展开文件区、不选择成员仓库，也不恢复此前子工作区。

紧凑模式仍停留在 scope 导航面；隐藏动作会激活工作区概览，但不引入桌面分割区状态。

### 默认工作区激活

以下入口遇到多仓库工作区时都选择根目录与工作区概览：

- 新打开工作区后的首次激活；
- 从另一个顶层项目切换回来；
- 使用项目循环切换进入工作区；
- 关闭当前项目后回退到另一个工作区；
- 应用启动时恢复活动工作区。

会话仍可保存运行期间的 `workspaceActiveContextByRoot`，供当前会话内的仓库和子工作区导航使用；恢复阶段会把工作区默认入口规范化为概览，不恢复保存的成员上下文。

若一个成员仓库同时作为独立顶层项目打开，显式激活该独立项目仍进入该 Git 仓库，因为其顶层项目身份不是多仓库工作区。

## 组件与状态

`RepoView` 继续拥有普通仓库与工作区概览的桌面文件区折叠状态，并提供稳定的 `collapseFileArea` 回调。

`RepoExplorerPane`、`PlainWorkspacePane`、`ActiveBranchWorkspaceView` 和 `BranchWorkspacePane` 只转发或组合该回调：

- 普通成员仓库和工作区概览直接转发到 `WorkspaceRepositoryRail`；
- 子工作区在隐藏前同时收起其局部文件区和 `RepoView` 的父级文件区状态，保证切回概览后文件区仍为收起状态。

`WorkspaceRepositoryRail` 不读取文件区是否已折叠。它使用幂等的 `onCollapseFileArea`，避免误用现有 toggle 回调导致已收起文件区被重新打开。

`activateProject` 将多仓库工作区直接激活为 Overview。关闭回退和会话恢复使用相同的顶层项目默认目标，不再通过保存的仓库上下文计算目标。

## 错误与边界

- 工作区根目录或工作区投影不存在时，现有 selection guard 保持无操作。
- 隐藏动作不执行服务端请求，不新增错误状态、缓存、持久化字段或 realtime 路径。
- 文件区收起回调缺失时仍可完成概览激活与列表隐藏，保持组件可复用性。
- 已保存的失效仓库或子工作区上下文不会影响默认入口；进入工作区后均从 Overview 开始。
- 成员仓库从配置中移除且当前上下文失效时，回退到 Overview，不自动选择另一个仓库。
- 关闭非活动项目不构成工作区激活或回退，必须保留当前工作区的成员上下文。

## 测试

1. 从可见状态隐藏仓库列表时，调用文件区收起意图、激活 Overview，并隐藏列表。
2. 从隐藏状态显示仓库列表时，不调用文件区收起意图，也不改变 Overview。
3. 隐藏动作从成员仓库上下文退出后，活动仓库为工作区根目录，活动上下文为 Overview。
4. `RepoView`、普通成员仓库和子工作区链路都把幂等收起回调传到 Rail。
5. 激活已记住成员仓库或子工作区的顶层工作区时，仍进入 Overview。
6. 项目循环切换和关闭项目后的工作区回退进入 Overview。
7. 会话恢复活动工作区时，活动仓库为根目录且上下文为 Overview；显式恢复独立成员仓库项目仍进入该仓库。
8. 工作区成员配置变化使当前成员失效时回退 Overview。
9. 关闭非活动项目时保留当前工作区成员上下文。
10. 运行目标 Vitest、`bun run typecheck`、`bun run check:architecture` 和 `bun run test`。

## 非目标

- 不删除运行期间选择仓库或子工作区的能力。
- 不删除 `workspaceActiveContextByRoot`，也不重构会话协议。
- 不改变工作区仓库列表可见性的按工作区持久化行为。
- 不改变子工作区列表自身的展开、排序或操作。
- 不改变独立仓库和普通目录项目的默认激活语义。

## 工程原则

- **KISS**：隐藏动作只组合三个直接意图，不引入观察 effect。
- **YAGNI**：不新增服务端字段、全局展示状态或恢复协议版本。
- **DRY**：所有顶层工作区入口共享同一 Overview 默认语义；文件区使用统一的幂等收起回调。
- **SOLID**：Rail 负责用户动作编排，Store 负责活动上下文，文件区 owner 负责局部展示状态。

## 架构拷问结论

- 文件区折叠继续属于 Local state，符合 `docs/state-sync.md`。
- 活动项目和工作区上下文继续走现有 Restorable state 边界，只调整恢复时的默认投影。
- 本次没有新增领域概念；“工作区概览”“文件区”“仓库”和“工作树”均沿用 `CONTEXT.md` 的既有语言，因此不修改词汇表。
- 决策局部、可逆且没有新的跨进程契约，不满足 ADR 条件。
