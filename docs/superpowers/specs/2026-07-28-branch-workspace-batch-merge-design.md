# 子工作区批量合并设计

**日期**：2026-07-28  
**状态**：已实施

## 背景

子工作区当前提供“合并回基准分支”动作。服务端已经能按清单顺序处理全部成员，并通过工作区失效通知报告当前仓库和 `pull / merge / push` 步骤；Renderer 也会在内联面板里显示这一瞬时状态。

现有入口不能选择本次要处理的成员，名称没有表达批量语义，而且进度只是每行的一段状态文字。用户需要从弹窗中选择尚未合并的成员工作树，启动一次有明确步骤反馈的顺序批量合并。

## 目标

1. 将用户可见动作从“合并回基准分支”改为“批量合并”。
2. 使用前台弹窗列出成员工作树及其 `目标分支 → 基准分支`，允许选择本次批次。
3. 默认选择所有尚未合并的成员；已经合并的成员保留可见但禁用。
4. 一次确认后按子工作区清单顺序自动执行所选成员，实时显示成员和 Git 步骤进度。
5. 失败时停止，不回滚已经完成的 Git 或远端写入；弹窗保留并允许从未完成步骤重试。

## 非目标

- 不改变批量提交、批量拉取和批量推送的内联面板。
- 不提供拖动排序；执行顺序继续由子工作区清单决定。
- 不并行执行成员，不提供原子事务或自动回滚。
- 不估算百分比、剩余时间或命令级进度。
- 不增加持久化选择、后台任务或 Electron 专用协议。

## 方案比较

### 方案 A：在现有 Git 动作组件中为合并增加专用弹窗（采用）

保留现有计划、执行、失效重读和 Git 写路径，只给 `merge-back` 增加成员选择协议和弹窗渲染。改动集中，其他 Git 动作不受影响，也不会复制服务端编排。

### 方案 B：把四种批量 Git 动作全部迁移到统一弹窗

表面更一致，但会无关地改变批量提交、拉取和推送的成熟交互，扩大测试和回归范围，不符合本次需求。

### 方案 C：新增一套独立的批量合并 API 与服务

边界最独立，但会复制现有合并计划、指纹校验、取消、重试和进度发布逻辑，违反 DRY，也增加两套语义漂移的风险。

## 交互设计

入口位于子工作区项目菜单，标签为“批量合并”。打开后立即请求完整合并计划，并在前台弹窗中显示加载状态。

计划就绪后：

- 每行显示复选框、仓库名称、`目标分支 → 基准分支` 和状态。
- 尚未合并的成员默认选中，可以在首次执行前取消或重新选择。
- 已经合并到基准分支的成员置灰，标注“已合并”，不可选。
- 没有选择成员时，两个开始按钮均禁用。
- “仅合并”只在各基准工作树中执行合并。
- “拉取、合并并推送”要求所有选中成员的基准分支都有可用上游；不满足条件的成员显示“无上游”，该按钮禁用，但“仅合并”仍可用。

开始后锁定成员选择和执行模式。弹窗显示“已完成 X/Y”，其中 Y 只统计所选成员。每个所选成员根据所选模式显示：

- 仅合并：`合并`。
- 拉取、合并并推送：`拉取 → 合并 → 推送`。

步骤状态为“等待 / 进行中 / 完成 / 失败”。服务端严格顺序执行，因此 Renderer 可以用 `completedCount`、当前仓库和当前步骤推断已经完成的前置步骤，不创建平行的服务端状态。

成功后沿用现有行为关闭弹窗。失败后保持弹窗打开：已完成成员与步骤保持完成，失败步骤显示失败，后续步骤等待；只显示原执行模式的重试动作。关闭执行中的弹窗会调用现有取消接口。

## 协议与服务端执行

`merge-back` 执行输入新增非空、去重的 `repositoryNames: string[]`。共享边界负责验证名称格式；服务端再验证所有名称都属于计划并且至少包含一个尚未合并的成员。

服务端按计划中的成员顺序过滤所选集合，不信任客户端顺序。`totalCount` 使用所选成员数量，`currentStep` 使用过滤后序号。

首次执行会把所选仓库集合和模式绑定到待执行计划。失败重试必须使用完全相同的集合和模式，以免已经完成 `pull` 或 `merge` 后切换策略产生不完整管线。已完成成员和当前成员已完成的步骤继续由既有 `completed` 与 `mergeProgress` 状态跳过。

执行前的指纹复核忽略未选成员，只验证选中且尚未完成的成员；子工作区成员身份和顺序仍必须与计划一致。这样无关成员的 Git 内容变化不会阻断本次批次，但成员配置变化仍会使计划过期。

结果继续返回完整计划成员状态以保持现有结果协议稳定；Renderer 对未选成员显示“未选择”，不把它们计入进度。

## 状态与数据流

1. Renderer 请求服务端生成全成员合并计划。
2. 弹窗把选择、已启动模式和首次执行前编辑状态保存在组件本地；这些状态不跨窗口同步，也不持久化。
3. Renderer 提交计划令牌、模式和所选仓库名称。
4. 服务端校验令牌与选择，顺序运行 Git 写路径，并在当前成员或步骤变化时发布已有工作区失效通知。
5. TanStack Query 通过已有 WebSocket invalidation + targeted refetch 读取 `activeOperation`。
6. 弹窗将服务端活动快照和最终结果投影为成员/步骤进度。

不新增轮询或流式协议。进度变化离散且已有运行时一致快照，符合项目 realtime 与 Renderer-first 约定。

## 错误与边界

- 空选择在客户端禁用，在共享输入和服务端再次拒绝。
- 重复、未知或不属于计划的仓库名称返回无效参数，不执行任何 Git 写入。
- 所选成员在计划后变为已合并、分支头变化、工作树变脏或成员配置变化时，执行前复核使计划过期。
- 已经合并的成员不允许显式选择，避免把纯拉取/推送伪装成合并。
- 远端模式只检查所选成员的上游就绪状态，未选成员不会阻塞。
- 首次写入后失败时不允许修改选择或模式；重试跳过已完成成员和步骤。
- 取消只中止尚可取消的当前/后续命令，不回滚已经完成的 Git 或远端写入。

## 测试策略

### 共享协议

- 接受非空、去重、规范的所选仓库名称。
- 拒绝空数组、重复名称和非法名称。

### 服务端写路径

- 只处理所选成员，且顺序由计划而非请求决定。
- 活动进度总数和序号只统计所选成员。
- 未选且状态变化的成员不阻断执行。
- 未知成员、全为已合并成员或远端模式中的所选无上游成员在任何写入前失败。
- 失败后以相同选择和模式重试时跳过已完成步骤。
- 失败后更换选择或模式被拒绝。

### Renderer

- 批量合并使用 Dialog portal，其他动作仍是内联面板。
- 默认选择所有未合并成员，已合并成员置灰。
- 空选择禁用执行；远端就绪只按选中成员计算。
- 提交包含选择，执行后锁定选择与模式。
- 活动快照显示所选成员完成计数与分步骤状态。
- 失败结果保留完成/失败/等待状态并只允许同模式重试。
- 四种语言字典键完整且中文入口为“批量合并”。

## 架构压力检查结论

- **Repository 边界**：每个成员仍是独立 Git 操作边界，选择只决定本批次包含哪些边界。
- **状态所有权**：选择和模式是短期本地状态；计划、活动操作和 Git 结果继续由服务端负责。
- **失败语义**：保持顺序、遇错停止、无回滚，并将重试约束绑定到首次批次。
- **分层**：传输解析、写路径编排和 UI 投影各自留在现有 feature slice 中。
- **实时**：复用 invalidation + refetch，不新增流式或 Electron 特例。
- **术语**：“批量合并”是面向用户的动作名称；领域术语继续使用 `Branch workspace merge-back`。

不创建 ADR：这是现有合并编排的局部、可逆扩展，没有新的长期架构边界。
