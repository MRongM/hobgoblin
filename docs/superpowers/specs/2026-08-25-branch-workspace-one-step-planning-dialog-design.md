# 子工作区选择与计划一步提交弹窗设计

**日期**：2026-08-25
**状态**：已实施

## 目标

把当前需要先选择、再点击“下一步”查看计划、最后确认执行的子工作区弹窗改为一步提交交互：宽屏左侧持续显示选择与配置，右侧自动显示与当前输入严格对应的计划和必要审批，用户只点击一次最终提交按钮。

“一步提交”只减少正常路径中的显式计划按钮，不减少安全步骤。服务端仍先生成只读计划，执行仍使用计划令牌，破坏性操作仍要求明确审批，执行前仍重新校验现场。

## 范围

本次覆盖六个具有选择或配置的交互：

- 新增子工作区；
- 增加成员工作树；
- 移除成员工作树；
- 删除整个子工作区；
- 添加子工作区依赖项；
- 移除子工作区依赖项。

以下流程不变：

- 修复子工作区；
- 批量提交、丢弃、完整远端对齐、修改 upstream、拉取、推送、合入和合出等批量 Git 操作。

代码与文档继续使用现有领域术语 **Branch workspace operation / 子工作区操作**、**Branch workspace dependency maintenance / 子工作区依赖维护** 和各个 **Branch workspace batch Git action / 子工作区批量 Git 操作**。不引入“工作区批量操作”这一含混概念。

## 当前问题

`BranchWorkspaceDialog` 的新增、扩展、缩减和删除模式以及 `BranchWorkspaceDependencyDialog` 的添加、移除模式都把同一短期交互拆成两个互斥页面：

1. 用户完成选择或配置；
2. 点击“下一步”请求服务端计划；
3. 选择页被计划页替换；
4. 用户检查计划、勾选审批，再次点击确认。

该结构迫使用户在选择和结果之间来回切换，也让“下一步”成为没有独立业务意图的机械步骤。计划本身仍然必要，但不需要由第二次导航式点击触发。

## 采用方案

### 宽屏双栏

弹窗保持固定头部和最终操作栏，主体采用约 `3:2` 的双栏布局：

- 左栏：当前操作的选择与配置；
- 右栏：自动生成的计划、风险说明、必要审批、计划错误和执行进度；
- 底部操作栏：取消与唯一的最终提交按钮，提交动作在视觉上与右栏对齐。

双栏各自滚动，头部与最终操作栏不随长仓库清单或长计划离开视口。弹窗使用接近可用视口的受限宽度和现有 `85vh` 高度边界，不引入全屏模式。

### 窄屏单栏

紧凑窗口和 Mobile Web 按“选择与配置 → 计划与审批”纵向排列，共用一个纵向滚动区和固定最终操作栏。交互仍是自动规划加一次最终提交，不显示“下一步”，也不强制双栏或产生横向滚动。

### 正常交互

1. 弹窗打开后立即显示左栏。
2. 当前输入尚不足以构造有效请求时，右栏显示引导空状态。
3. 输入有效后自动请求只读计划。
4. 右栏只展示与当前输入完全一致的计划。
5. 用户完成计划要求的审批后，点击一次最终提交。
6. 执行成功沿用现有关闭和查询更新行为。

依赖添加继续使用 `Skip / Copy / Symlink` 选择，依赖移除和成员缩减继续使用复选框。新增和扩展继续保留仓库选择、创建基准、创建前同步、仓库依赖及根依赖配置。删除整个子工作区时，左栏持续展示删除本地分支与远端分支选项及危险提示，选项变化自动刷新右栏删除计划。

## 自动规划状态机

右栏只有以下互斥状态：

```text
incomplete  输入不足，提示先完成左栏
planning    正在检查当前输入
ready       当前输入对应的计划与审批
error       当前输入的计划失败，可重试或修改输入
executing   锁定输入并投影执行进度
failed      保留计划、进度和安全恢复动作
```

计划就绪必须同时满足：

- 当前表单可以构造合法请求；
- 当前模式、目标子工作区和固定成员入口对应的本地默认状态已经初始化；
- 所有会影响请求的前置读取已经结算；
- 成功计划绑定的请求身份等于当前请求身份；
- 当前计划令牌尚未被后续计划替换。

任何条件不满足时，最终提交按钮均不可用。旧计划不得在输入变化后继续作为当前确认内容；右栏切换为“正在检查”，避免用户确认视觉上已经过期的事实。

### 触发节奏

- 复选框、开关、分支选择、复制/软链接选择等离散变化立即安排重新规划。
- 分支名称等自由文本输入等待 300ms 稳定后再规划。
- 相同规范化请求不重复规划。
- “同步全部仓库”、依赖候选刷新等可能改变计划事实但不改变请求 JSON 的动作结算后递增本地计划修订号，强制重新规划。
- 已选仓库的依赖读取尚未结束时暂停规划，避免用户在候选尚未出现时提交一个意外省略依赖的计划。

### 单飞与最新输入

自动规划必须是每个弹窗单飞、最新输入优先：

1. 同一弹窗最多只有一个服务端计划构建正在运行。
2. 输入变化会取消当前 HTTP 计划请求。
3. 新请求只在旧请求结束或确认取消后开始。
4. 连续变化只保留最新的规范化请求，中间请求不执行。
5. 每个响应携带 Renderer 本地请求身份；过期响应不能更新计划、错误或 pending 状态。
6. 因输入变化或关闭弹窗导致的取消不显示错误。

生命周期计划客户端新增可选 `AbortSignal`，路由把请求信号传给已经支持取消的 `buildBranchWorkspacePlan`。依赖计划客户端同样传递信号，复用服务端现有取消边界。共享请求和计划协议不增加字段；请求身份仅属于 Renderer 的短期协调状态。

## 审批与提交安全

- 计划要求的审批继续由服务端权威 `requiredApprovals` 决定。
- 当前请求身份或计划令牌变化时立即清空全部审批。
- 缩减成员、移除依赖以及覆盖现有依赖目标继续使用 destructive 样式。
- 删除整个子工作区继续使用 destructive 样式，并保留独立的强制删除入口；强制删除同样只能使用当前可见计划及已满足的审批。
- 最终提交始终只发送当前可见计划的令牌和当前审批。
- 服务端执行前继续重建计划或校验指纹；计划过期绝不自动执行新计划。
- 计划过期时自动刷新右栏并要求用户再次确认，不能在后台重规划后替用户继续写入。
- 计划请求 pending 与写入执行 pending 分开表达。关闭一个正在规划的弹窗只取消计划读取；关闭或取消一个正在执行的操作继续使用该操作原有的中止语义。

因此，一步交互不把“计划并执行”合并为一个不透明服务端命令，也不把审批降级为提交后的通知。

## 执行与失败恢复

### 新增与扩展

最终提交开始后锁定左栏及审批，右栏沿用现有步骤进度。失败时保留当前计划、完成步骤、错误和重试动作。

若用户要改变未完成意图，使用异常恢复动作“修改选择”：

1. 定向重读最新子工作区快照；
2. 把已完成成员和条目投影为固定基线；
3. 清除旧计划、结果和审批；
4. 重新开放左栏；
5. 对新的有效选择自动规划。

该动作替代当前正常流程语境中的“返回上一步”，但仍只在创建或扩展失败后出现。它不会回滚已完成工作。

### 缩减

缩减一旦开始，左栏保持锁定。失败后只允许沿用现有计划重试或取消/关闭，不允许通过编辑选择替换中断的缩减意图，继续遵守现有不可重新规划边界。

### 删除整个子工作区

删除开始后锁定左栏和关闭入口，右栏继续投影成员清理、分支清理及目录删除进度。失败后保留当前计划和已完成进度，可沿用原计划重试或关闭；强制删除仍是同一弹窗内的独立 destructive 异常动作，不绕过当前计划匹配和审批检查。

### 依赖维护

- 执行前失败且没有完成条目时，可以沿用当前计划重试。
- 出现部分完成或计划过期时，不直接重试旧计划；显示异常恢复动作“重新检查”。
- “重新检查”重读实时候选，移除已完成选择，清除旧计划和审批，再由自动规划生成剩余工作的当前计划。
- 已完成的复制、软链接或删除永不回滚，也不会被自动转换成覆盖同名目标的新操作。

正常路径不出现“检查计划”按钮；“修改选择”和“重新检查”只处理已经失败或变化的异常现场，不构成第二个正常提交步骤。

## 既有行为保留

- 新增弹窗的“同步全部仓库”在执行开始前持续可用，即使右栏已有计划；同步期间表单仍可编辑，但最终提交暂停，结算后强制重新规划。
- 创建完成但最终远端读取瞬时失败时，继续使用 ready 实时快照和完整步骤进度关闭弹窗。
- 创建和扩展的完成成员继续成为不可修改的固定基线。
- 成员级固定缩减入口继续预选并锁定精确成员。
- 依赖覆盖仍绑定目标指纹；外部根复制仍要求审批；软链接删除仍不跟随目标。
- 关闭、取消、进度、查询失效和成功 toast 继续沿用现有所有者。
- 删除整个子工作区的本地/远端分支选项、执行期不可关闭、失败后重试以及强制删除安全语义保持不变。
- 修复以及全部批量 Git 弹窗保持当前交互和安全语义。

## 组件与状态所有权

### Renderer

- `BranchWorkspaceDialog` 继续拥有新增、扩展、缩减、整个子工作区删除的表单状态和请求构造。
- `BranchWorkspaceDependencyDialog` 继续拥有依赖选择和审批状态。
- 两个弹窗复用一个仅负责布局的响应式“选择 + 计划”外壳，不把不同领域请求抽象成通用协议。
- `useBranchWorkspaceActions` 与 `useBranchWorkspaceDependencyActions` 继续拥有传输、计划、执行、错误和失效编排，并明确区分 `planning` 与 `executing`。
- 一个窄职责的 latest-plan 协调辅助负责防抖、取消、单飞和过期响应隔离；它不理解仓库、依赖或审批。
- 计划请求身份、修订号、搜索输入、审批和展开状态全部属于 Local state，不进入 Zustand、不持久化、不跨窗口同步。

### Server 与共享层

- 服务端计划和执行服务仍拥有权威计划、令牌、指纹、审批要求与执行前重建。
- 生命周期计划路由只补齐已有 `AbortSignal` 传递，不改变业务协议。
- 依赖计划继续使用现有 signal、确定性令牌和写路径。
- `src/shared/**` 不增加 UI 布局、请求身份或防抖概念。

该分层符合 `docs/layering.md`：UI 不接管写入编排，短期交互保留在功能组件和现有 hooks；也符合 `docs/state-sync.md`：服务端计划是运行时事实，弹窗协调状态是本地状态。

## 可访问性与文案

- 左右区域使用可见小标题；右栏计划状态使用 `aria-live="polite"`，但输入变化不抢夺焦点。
- 所有复选框、开关、选择器和审批保持明确的可访问名称。
- 键盘 Tab 顺序先经过左栏，再经过右栏审批，最后到固定操作栏。
- 自动规划完成后不自动聚焦提交按钮，避免打断连续配置。
- 执行中对锁定控件使用真实 `disabled`，并保留可读的计划与进度。
- 中文继续使用“子工作区”“成员工作树”和“依赖项”，不使用“子仓库”。
- 四种语言新增“选择与配置”“操作计划”“完成左侧选择后自动检查”“正在更新计划”“修改选择”“重新检查”等文案。
- `workspace.branch-workspace.preview` 仍供不在本次范围内的修复流程使用，不能全局删除或改义。

## 测试与验收

### 最新计划协调

- 自由文本在 300ms 内的连续输入只请求最终值。
- 离散选择立即安排规划。
- 同一请求不重复规划；修订号变化会强制规划。
- 新输入取消旧请求，并在旧请求结算前不并发启动下一请求。
- 过期成功、失败和 finally 均不能覆盖当前计划、错误或 pending。
- 关闭弹窗取消计划且不产生错误。

### 生命周期弹窗

- 新增、扩展、缩减和整个子工作区删除同时渲染左侧选择与右侧计划，不渲染正常路径“下一步”。
- 无效输入显示引导状态；规划中、失败、就绪和执行中状态互斥。
- 当前计划不匹配输入、前置读取未完成或审批缺失时不能提交。
- 请求或 token 变化清空审批。
- 最终提交只调用一次现有 execute，携带当前计划令牌与审批。
- 新增/扩展失败可“修改选择”并使用最新完成基线；缩减失败仅允许重试。
- “同步全部仓库”结算后强制重新规划，期间不能提交旧计划。
- 删除选项始终与计划同屏，切换选项会自动规划；自动规划期间允许修改或关闭，执行期间保持锁定。
- 删除仍保留默认勾选本地分支、远端分支依赖本地分支、破坏性确认、强制删除、失败重试及执行进度。
- 修复仍保留现有“下一步”交互。

### 依赖弹窗

- 添加和移除同时显示选择与计划，无正常路径“下一步”。
- 添加覆盖目标和移除使用 destructive 提交；外部根复制审批仍生效。
- 部分完成后不能重试旧计划；重新检查会清除已完成选择并规划剩余项。
- 计划过期只刷新计划，不自动执行。
- 候选读取、计划读取和执行 pending 被正确区分。

### 布局、字典和回归

- 宽屏为约 `3:2` 双栏、独立滚动和固定头尾；窄屏为无横向滚动的单栏顺序。
- 计划状态具备 live region，自动更新不移动焦点，锁定控件使用 `disabled`。
- 英文、简体中文、日文和韩文字典键一致。
- `BranchWorkspaceGitActionDialog` 行为与测试不变。
- 运行目标 Vitest、`bun run typecheck`、`bun run check:architecture` 和 `bun run test`。

## 方案取舍

### 未采用：最终点击后在后台计划并立即执行

该方案虽然只有一次点击，却无法让用户在写入前检查精确步骤和审批，实质上绕过了现有安全模型。

### 未采用：保留“检查计划”，只把两个页面并排

该方案改善了上下文，但没有消除机械的第二步，不满足一步提交目标。

### 未采用：每次输入变化并发请求计划

生命周期计划会读取多个本地或远端仓库，依赖计划还会检查和指纹化路径。并发请求既浪费资源，也可能让较旧响应覆盖服务端 pending plan。

### 未采用：把选择、计划和审批存入全局 Store

这些状态只服务一次弹窗交互，不需要跨窗口一致或重启恢复。全局化会增加失效与清理复杂度。

## 工程原则与文档结论

- **KISS / YAGNI**：只改六个已有选择或配置流程；不统一所有弹窗，不新增协议字段、持久化或后台任务。
- **DRY**：复用一个布局外壳和一个 latest-plan 协调辅助；领域请求、计划内容和恢复规则保持各自实现。
- **SOLID**：组件负责表单投影，hooks 负责传输和 mutation 编排，服务端负责计划与安全校验，共享层只保留跨边界协议。
- **安全**：减少的是显式导航点击，不是计划、审批、令牌、指纹、执行前重建或失败恢复。

现有 `CONTEXT.md` 已准确区分子工作区操作、依赖维护和批量 Git 操作，本设计没有新增领域概念，因此不修改词典。该改动是现有交互和请求协调的局部、可逆调整，不满足 ADR 的“难以逆转”条件，因此不创建 ADR。
