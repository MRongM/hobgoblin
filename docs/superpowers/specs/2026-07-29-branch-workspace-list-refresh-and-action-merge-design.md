# 子工作区列表刷新与隐藏主工作区动作合并设计

**日期**：2026-07-29  
**状态**：已授权自主实施

## 问题

子工作区列表当前只有读取失败时的“重新加载”入口。正常加载成功后，用户无法显式重新读取整个列表，
因而不能主动获取外部产生的新增、删除、成员变化或漂移状态。

工作区仓库列表隐藏后，现有实现把完整的工作区仓库标题栏动作迁移到子工作区标题栏，其中包括
“配置工作区”和“重新扫描仓库”。这些动作属于主工作区仓库列表，不应伪装成子工作区动作；同时，
迁移后的图标与底部状态栏动作分占两行，没有形成隐藏主工作区后的紧凑动作区。

## 目标

- 子工作区标题栏始终提供图标式“重新加载子工作区”，用于重新读取整个子工作区列表。
- 刷新期间显示忙碌状态并阻止重复请求；失败时保留现有快照或错误，允许再次刷新。
- 主工作区仓库列表隐藏后，把子工作区相关动作并入底部状态栏的图标组。
- “配置工作区”和“重新扫描仓库”只在主工作区仓库标题栏显示，不迁移到子工作区标题栏或状态栏。
- 保留恢复主工作区仓库列表的入口。

## 方案比较

### 采用：子工作区标题栏保留刷新，其他子工作区动作并入底部状态栏

子工作区标题栏只承担列表身份与列表刷新。隐藏主工作区后，“创建子工作区”“批量拉取”和“显示工作区仓库”
进入底部状态栏现有图标组；设置、主题、终端和文件区动作继续由状态栏拥有。

该方案符合现有桌面 shell 对底部状态栏的定位，避免窄标题栏堆叠过多图标，也让主工作区动作与子工作区动作
保持清晰边界。

### 不采用：把状态栏动作全部移到子工作区标题栏

这会削弱底部状态栏在普通仓库、主工作区和子工作区之间的一致性，并在窄侧栏造成图标拥挤。

### 不采用：只删除配置与扫描动作，不合并图标

改动最小，但仍保留上下两组分离的图标，未满足隐藏主工作区后合并动作区的要求。

## 交互

### 主工作区仓库列表可见

- 主工作区标题栏保留：创建子工作区、批量拉取、配置工作区、重新扫描仓库、隐藏工作区仓库。
- 子工作区标题栏新增：重新加载子工作区列表。
- 底部状态栏保持现状。

### 主工作区仓库列表隐藏

- 子工作区标题栏仅显示列表标题与重新加载按钮。
- 底部状态栏在现有图标后合并：创建子工作区、批量拉取、显示工作区仓库。
- 不显示配置工作区与重新扫描仓库。
- 重新显示主工作区后，合并动作自动回到主工作区标题栏。

### 列表刷新

- 点击刷新调用当前根节点的 `branchQuery.refresh()`，不调用工作区仓库扫描。
- 刷新期间刷新图标旋转并禁用同一动作；读取失败后恢复可用。
- 错误行已有文字式重新加载入口继续复用同一 pending 状态与刷新函数。

## 组件与数据流

`WorkspaceRepositoryRail` 继续拥有工作区与子工作区动作、弹窗和查询编排。为避免把这些职责提升到
`BranchWorkspacePane`，底部 `StatusBar` 提供一个窄的动作挂载点；Rail 仅在工作区仓库列表隐藏时，
把子工作区动作通过 React portal 渲染到该挂载点。

```text
BranchWorkspacePane
  ├─ WorkspaceRepositoryRail
  │    ├─ visible: workspace header actions + branch-list refresh
  │    └─ hidden: branch-list refresh + portal(branch actions)
  └─ StatusBar
       ├─ existing status actions
       └─ branch action portal host

refresh button
  -> useBranchWorkspaceQuery.refresh(rootId)
  -> existing workspace read endpoint
  -> authoritative branch workspace snapshot
  -> TanStack Query projection rerender
```

挂载点只是局部展示连接，不保存状态、不跨窗口同步，也不改变服务端契约。工作区仓库是否可见继续使用现有
restorable store 字段。

## 错误、安全与生命周期

- 刷新是只读操作，不修改配置、注册表、目录、工作树或 Git 状态。
- 不增加轮询、文件监听、realtime 事件、服务端 API 或依赖。
- portal 目标卸载时动作随 React 树自然移除；紧凑界面切换表面时不保留陈旧 DOM。
- 若某个独立 Rail 调用点未提供状态栏挂载点，隐藏动作回退到子工作区标题栏，确保“显示工作区仓库”始终可达；正式的子工作区 Pane 提供挂载点，因此正常界面仍使用合并布局。
- 配置与仓库扫描能力没有删除，只在主工作区仓库列表可见时出现。
- 现有错误行清理注册表、单个子工作区“刷新改动”和自动漂移重读语义保持不变。

## 测试

1. `WorkspaceRepositoryRail`：正常列表标题栏显示手动刷新；点击只调用子工作区查询刷新并防止重复请求。
2. 主工作区可见时，配置与扫描仍只在主工作区标题栏，状态栏挂载点为空。
3. 主工作区隐藏时，子工作区标题栏不含配置、扫描、创建、拉取或显示主工作区动作；后三者渲染到状态栏挂载点。
4. 重新显示主工作区后，portal 动作回到主工作区标题栏。
5. `StatusBar`：可接收动作挂载点而不改变现有设置、主题、终端、文件区和分支摘要行为。
6. 字体契约继续验证所有项目标题栏动作使用 `icon-sm`。
7. 运行针对性 Vitest、`bun run typecheck`、`bun run check:architecture` 和 `bun run test`。

## 非目标

- 不更改单个子工作区 More 菜单中的“刷新改动”。
- 不把手动列表刷新扩大为仓库发现、Git status、fetch 或 pull。
- 不重构工作区查询层、状态栏全部动作或通用 portal 系统。
- 不新增设置、快捷键、持久化字段或移动端专用交互。

## 工程原则

- **KISS / YAGNI**：复用现有刷新函数和状态，不增加协议或状态层。
- **DRY**：标题栏图标与错误行复用同一刷新编排；动作只定义一次，再按可见状态投影到不同容器。
- **SOLID**：Rail 继续负责工作区动作，StatusBar 只提供展示挂载点，不接管业务编排。

本改动没有新增领域术语或长期架构决策，不需要更新 `CONTEXT.md` 或新增 ADR。

## 架构拷问结论

- **外部创建或删除子工作区**：手动刷新读取权威快照，覆盖该场景；无需仓库扫描。
- **刷新时主工作区被重新显示**：pending 状态属于 Rail，动作换位不启动第二个请求，也不会丢失完成状态。
- **空列表或读取错误**：标题栏刷新仍可用；错误行按钮继续显示同一读取动作。
- **配置或扫描仍需访问**：用户先通过状态栏“显示工作区仓库”，再从主工作区标题栏执行，避免跨领域放置动作。
- **跨窗口一致性**：读取结果仍由服务端权威状态与查询缓存收敛；portal 只决定当前 renderer 的展示位置。
- **领域模型**：本次只调整既有“子工作区”“工作区仓库列表”和“状态栏”的交互，不修改定义，因此不更新 glossary。
