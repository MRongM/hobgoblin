# Hobgoblin v2.2.1 Workspace and Linux Release Design

## Goal

Release Hobgoblin v2.2.1 with a coherent workspace-development story across every public language, a first-class Linux Server Mode source deployment archive, explicit Android and tmux coverage, an updated GitHub Pages site, and a verified GitHub Release.

## Canonical product language

Public documentation must follow the domain model in `CONTEXT.md`:

- A **multi-repository workspace** is one project rooted at a non-Git directory whose configured members are independent Git repositories.
- A **branch workspace** is a branch-specific working context owned by one configured workspace. It groups selected same-named repository worktrees while every member remains an independent Git operation boundary.
- “Subworkspace” is not a public canonical term. Localized prose may explain the parent/child relationship, but it must name the concept as **Branch workspace**.

The recommended development flow is:

1. Open or configure a multi-repository workspace and choose its repository members.
2. Create a branch workspace with one common branch name and an explicit base branch per selected repository.
3. Materialize optional workspace dependencies by copy or symbolic link.
4. Develop from the branch-workspace root or a member worktree, keeping AI CLI and terminal sessions attached to that context.
5. Run repository-scoped operations for one member or ordered branch-workspace commit, pull, push, merge-in, and merge-out operations across selected members.

Cross-repository operations must be described accurately: they run sequentially, isolate repository-member failures so later members continue, aggregate failures at the end, retain completed member results, and do not roll back automatically.

## Linux Server Mode source archive

Add `scripts/build-linux-source-archive.ts`. It creates:

```text
Hobgoblin-<version>-linux-source.tar.gz
└── Hobgoblin-<version>/
```

The version comes from `package.json`. The archive includes only tracked files required to build and run Server Mode:

- `src/server/**`
- `src/shared/**`
- `src/system/**`
- `src/web/**`
- `assets/**`
- `LICENSES/**`
- `THIRD_PARTY_NOTICES.md`
- all four public README files
- `package.json` and `bun.lock`
- `tsconfig.json`, `tsconfig.main.json`, and `tsconfig.web.json`
- `vite.config.ts`
- `serve.sh`
- `scripts/start-server.ts`
- `scripts/serve-systemd.sh`

Exclude test files, snapshots, Android sources, Electron main/preload sources, desktop packaging files, planning documents, Git metadata, the historical Git bundle, dependencies, and generated output. Preserve executable modes on shell and entrypoint scripts.

The script must fail for an invalid package version, a missing required entrypoint, an empty tracked-file selection, a copy failure, or a tar failure. It builds in a temporary directory, validates required archive members, writes the archive to an explicit output directory, and always removes temporary staging data.

## Release workflow

Extend `.github/workflows/release.yml` with a `build-linux-source` job:

- Run on Ubuntu.
- Check out the selected ref.
- Set up Node.js 24.
- Run `node scripts/build-linux-source-archive.ts --output-dir release`.
- Upload `release/Hobgoblin-*-linux-source.tar.gz` as the `hobgoblin-linux-source` workflow artifact.

Make `publish` depend on macOS, Windows, Android, and Linux jobs. Add `Hobgoblin-${VERSION}-linux-source.tar.gz` to release-asset validation and upload. Keep the workflow manual. Its generic notes explain that Linux users need Node.js 24+ and Bun and can run `scripts/serve-systemd.sh`; version-specific highlights remain in a separate v2.2.1 English notes file so future releases do not inherit stale claims.

## Test strategy

Use test-first development for executable and workflow behavior:

1. Add an archive behavior test that runs the new script in a temporary output directory, lists the real tarball, and asserts required and forbidden entries.
2. Run the test before creating the script and confirm it fails because the script/archive does not exist.
3. Implement the minimum packaging script and rerun to green.
4. Extend the release workflow contract test before modifying the workflow; confirm the expected Linux job and asset assertions fail, then update the workflow.
5. Update the Android identity contract before changing the Android version; confirm red, then update the active version configuration.
6. Add a documentation parity contract that requires every README and all Pages locales to mention Branch workspace, Android, tmux, and the Linux source archive.

Final verification commands:

```sh
bun run typecheck
bun run test
bun run check:architecture
bun run format:check
node scripts/build-linux-source-archive.ts --output-dir /tmp/hobgoblin-linux-release-check
```

Socket-binding tests that fail with sandbox `EPERM` must be rerun outside the sandbox. The archive must also be inspected with `tar -tzf` before publication.

## Integration and publication

The current feature branch is both ahead of and behind `main`. Before publication, merge `main` into the feature branch, resolve documentation conflicts in favor of the complete localized v2.2.1 content, and rerun verification. Then merge the feature branch into `main` with an explicit merge commit and verify the merged result again.

After the final safety confirmation:

1. Create atomic Conventional Commits for the approved changes.
2. Merge into `main` and push `main`.
3. Create and push annotated tag `v2.2.1` at the verified `main` commit.
4. Dispatch `release.yml` with ref `v2.2.1` and monitor it to completion.
5. Set the Release title to `Hobgoblin v2.2.1` and replace its notes with `docs/releases/v2.2.1.md`.
6. Monitor the automatically triggered Pages workflow; dispatch it manually on `main` only if no automatic run appears.
7. Verify the Release asset inventory and the deployed Pages URL.

Never overwrite an existing v2.2.1 tag or release. If publication fails after a tag is pushed, retain remote state and report the exact failure before considering any tag rewrite or deletion.
