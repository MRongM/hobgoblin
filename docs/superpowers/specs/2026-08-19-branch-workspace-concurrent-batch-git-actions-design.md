# 子工作区批量 Git 并发执行设计

**日期**：2026-08-19  
**状态**：已确认，授权当前会话内自主实施

## 背景

子工作区的批量提交、批量拉取、批量合入和批量合出目前按成员清单顺序串行执行。成员失败已经能够隔离并汇总，重试也会跳过成功成员并延续合并步骤，但仓库数量增加后，互不依赖的本地 Git 和网络等待会线性叠加。

本文取代既有设计中针对这四类动作的“成员串行执行”约束。批量推送、批量丢弃和批量设置上游不在本次范围内，继续保持当前行为。

## 目标

1. 批量提交、批量拉取、批量合入和批量合出的不同仓库成员支持并发执行。
2. 单个仓库成员内部仍按真实 Git 管线严格串行，例如 `pull → fetch → merge → push → cleanup`。
3. 同时运行的成员最多为 4 个，避免无界占用 CPU、磁盘、SSH 连接和网络带宽。
4. 保留计划校验、失败隔离、结果顺序、完成集、步骤恢复、冲突现场和显式取消语义。
5. 前台进度能够同时标记多个正在运行的成员及其当前步骤。

## 方案比较

### 采用：固定上限的成员管线并发

使用现有 `p-limit` 依赖，以 4 为固定并发上限。每个任务处理一个仓库成员的完整管线；共享执行器只负责调度、取消门控和最终等待。成员内部的业务步骤仍由方向专属执行函数拥有。

该方案保留当前以成员为单位的失败、重试和清理边界。一个慢仓库不会阻塞其他空闲并发槽位，结果仍按计划成员顺序投影。

### 不采用：无界 `Promise.all`

它实现简单，但大型工作区会同时启动所有 Git/SSH 操作，无法给磁盘、进程数和远端连接提供稳定上限。取消时也更难说明还有多少在途任务。

### 不采用：按步骤设置全局屏障

例如先并发拉取全部成员，再并发合并全部成员。该方案会让一个慢成员阻塞所有其他成员进入下一阶段，并把现有按成员保存的 `mergeProgress`、冲突现场和临时工作树清理拆散到多个全局阶段，重试模型更复杂。

## 并发与仓库隔离

- 并发单位是一个计划中被选中的仓库成员。
- 同一子工作区计划不会包含同一仓库的多个成员，因此并发任务不会写入同一 Git 仓库。
- 批量提交和批量拉取是单步骤成员管线。
- 批量合入和批量合出是多步骤成员管线；不同成员可以处于不同步骤。
- 成员开始顺序遵循计划顺序，但完成顺序由实际运行决定。
- 权威结果继续按计划顺序返回，不暴露 Promise 完成顺序。
- 并发上限是服务端常量，不增加设置项、协议输入或持久状态。

## 失败、完成与重试

- 成员失败只终止该成员管线；其他运行中或排队成员继续。
- `completed` 只记录成功成员，失败成员保留为同一执行身份下的可重试对象。
- `mergeProgress` 继续按仓库名记录已拉取、已获取、已验证、已合并或已推送步骤。
- 并发任务只写入各自仓库名对应的完成、失败、进度和临时工作树条目。
- 最终结果继续使用现有统一部分失败文案和逐成员失败详情。
- Git 写入不提供跨仓库事务，也不回滚其他成员已经完成的操作。

## 取消与清理

- 一个批次仍共享一个 `AbortController`。
- 取消后，尚未取得并发槽位的任务在启动时发现信号已终止，不执行 Git 写入。
- 已在途的底层操作接收同一信号并结算；成功完成的不可回滚写入仍记入完成集。
- 多步骤管线在每个 `await` 后再次检查取消信号，不启动后续 Git 步骤。
- 批量合出的应用临时工作树在返回取消结果前继续执行既有安全清理；普通已有工作树和合并冲突现场不自动清理。
- 服务端等待所有已调度成员完成或跳过后再移除活动操作并发布仓库失效，避免后台写入逃逸出请求生命周期。

## 活动进度模型

`BranchWorkspaceActiveOperation` 新增可选 `activeMembers` 与 `completedRepositoryNames`：

```ts
interface BranchWorkspaceActiveMemberOperation {
  repositoryName: string
  step: BranchWorkspaceGitActionStep
}

interface BranchWorkspaceActiveOperation {
  // 既有字段保持兼容
  activeMembers?: BranchWorkspaceActiveMemberOperation[]
  completedRepositoryNames?: string[]
}
```

- 服务端以计划顺序发布当前运行成员列表。
- `completedCount` 仍只统计成功成员；`completedRepositoryNames` 给出对应仓库身份，支持成员乱序完成时的精确投影。
- `currentStep` 改为单调递增的已启动成员数，并保持不超过 `totalCount`。
- 既有 `repositoryName` / `step` 与仅有 `completedCount` 的快照保留为顺序动作和兼容回退；并发投影优先读取精确成员字段。
- Web 端的通用批量进度投影按仓库名读取活动步骤，因此提交、拉取、合入和合出无需各自复制并发判断。
- 活动进度是服务端拥有的 runtime-coherent 临时状态，不持久化、不轮询。

## 分层与文件职责

- `src/server/modules/branch-workspace-git-action-write-paths.ts`：并发调度、成员管线、取消、完成/失败聚合与活动快照。
- `src/shared/branch-workspaces.ts`：共享活动成员步骤与已完成成员身份。
- `src/shared/server-invalidation.ts`：跨窗口失效事件的严格运行时校验。
- `src/web/components/repo-workspace/branch-workspace-batch-progress.ts`：多活动成员的 UI 进度投影和旧快照回退。
- `CONTEXT.md`：更新四类批量动作的领域定义。

不增加 Renderer 编排、后台任务、全局 store、Electron 专用路径、新依赖或新设置。

## 测试与验收

1. 批量提交在 4 个槽位内同时启动多个成员，并且一个失败不阻塞其他成员。
2. 批量拉取并发执行选中成员，保留未选择成员和重试语义。
3. 批量合入的不同成员可同时运行，但每个成员内部步骤顺序不变。
4. 批量合出的不同成员可同时运行，并分别拥有、清理自己的临时工作树。
5. 任意动作的峰值在途成员数不超过 4。
6. 取消后不启动排队成员的新 Git 写入；在途批量合出完成必要清理。
7. 结果成员顺序仍与计划一致，与实际完成顺序无关。
8. 活动快照可同时发布多个成员步骤，失效协议拒绝重复、空或非法成员项。
9. Web 进度同时把多个成员标为活动，并继续兼容旧的单成员快照。
10. 目标测试、`bun run typecheck`、`bun run check:architecture`、`git diff --check` 和全量 `bun run test` 完成验证。

## 架构压力检查结论

- **仓库边界**：并发只跨不同仓库，单仓库 Git 管线不并行。
- **写入所有权**：服务端写路径继续拥有计划、执行和取消；Renderer 只投影状态。
- **安全清理**：临时工作树仍由产生它的成员管线清理，其他任务不接触该路径。
- **失败确定性**：Promise 完成顺序不进入结果协议，最终结果按计划顺序投影。
- **资源边界**：固定并发 4，拒绝用户可调和无界并发。
- **状态同步**：复用现有 invalidation + refetch，不新增流式通道。

不创建 ADR：该决策局限于现有批量 Git 写路径，使用固定常量且容易在同一模块内调整，不满足难以逆转的条件。
